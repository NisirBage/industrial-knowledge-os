# IKIOS Benchmark Report

Generated by `backend/scripts/generate_benchmark_reports.py`, seed=42, 60 synthetic documents.
All numbers below are computed by actually running the production components — none are hand-typed.

## Methodology & ground truth assumptions (read this before citing a number below)

- **Dataset**: seeded, deterministic synthetic documents from
  `app/research/datasets/generator.py` — not real industrial documents.
  Real-world paraphrased text would score entity/relation extraction
  lower than these numbers suggest.
- **Retrieval ground truth is single-document per query**: each query is
  matched to exactly the one document it was generated from, even though
  several documents in the corpus may plausibly be relevant to it in
  reality. Recall@k here measures "found the one document we know is
  relevant," not "found everything a human would consider relevant."
- **Synthetic documents are ingested as one chunk each**, not run through
  the real multi-chunk `chunk_pages()` splitter production ingestion
  uses — a structural difference from real ingestion, not just a scale
  difference.
- **Environment-dependent results are labeled inline** (⚠️) rather than
  silently reported — e.g. the regex-vs-GLiNER comparison below is a
  known tie in environments where GLiNER can't load.
- None of the comparisons below should be read as a general claim about
  production accuracy — they measure the named components against the
  named synthetic ground truth, nothing broader. See each section's own
  numbers for what was actually measured, and the detailed limitations
  at the bottom of this report for the specific mechanisms behind each
  caveat.

## Optimization benchmarks (O1 / O1.2)

[docs/architecture/retrieval-optimization.md](../architecture/retrieval-optimization.md)
for what each optimization layer does; these numbers are what actually ran.

| Benchmark | Sample size | Key metrics |
|---|---|---|
| ranking_quality | 12 synthetic labeled queries | rrf_mrr=0.4583, ltr_mrr=0.5625, rrf_recall_at_5=1.0, ltr_recall_at_5=1.0 |
| context_compression | 14 synthetic evidence items (4 exact duplicates injected) | original_count=14, compressed_count=10, compression_ratio=0.7143, token_reduction≈28.6% |
| evidence_deduplication | 10 hand-labeled pairs (5 true duplicates, 5 distinct) | precision=1.0, recall=0.8, f1=0.8889 |
| entity_resolution | 6 hand-labeled (candidate, known-entity, should_merge) triples | precision=1.0, recall=1.0, f1=1.0 |

**Honest reading of `ranking_quality`**: the LTR ranker beating RRF here
(0.5625 vs 0.4583 MRR) confirms the training→inference pipeline works
end-to-end, not that LightGBM LambdaMART beats RRF on realistic queries —
the synthetic BM25 signal used to build labels is deliberately strong (5x
weight on relevant candidates), which is an easier setup for a
feature-based ranker than real, noisier production queries. A genuine
RRF-vs-LTR comparison needs real query logs (tracked in the roadmap).

**Honest reading of `evidence_deduplication`**: recall of 0.8 (not 1.0)
means one of the five true-duplicate pairs in the hand-labeled set was not
flagged by `near_duplicate_score()` at the benchmark's threshold — reported
as-is rather than tuning the threshold to the test set.

**Parallel executor and caching are deliberately excluded from this table**:
their benefit is wall-clock latency reduction under concurrent I/O, which a
synthetic in-process benchmark can't measure honestly (no real network/DB
latency to parallelize against). Their proof lives in
`tests/test_hybrid_retrieval_parallel.py`,
`tests/test_task_graph_executor_parallel.py`, and
`tests/test_hybrid_retrieval_caching.py` — real `time.sleep()`-based fakes
and call-counting assertions, not benchmark-suite metrics. See
[docs/architecture/retrieval-optimization.md](../architecture/retrieval-optimization.md#component-4--parallel-retrieval-executor)
for what those tests actually prove.

## Reasoning benchmarks (O2)

Run via `app/research/benchmarks/reasoning_runners.py` against small
self-contained synthetic/hand-labeled input, same discipline as the O1/O1.2
optimization benchmarks above. See
[docs/architecture/reasoning-verification.md](../architecture/reasoning-verification.md)
for what each component does; these are the real numbers from the last
verified run.

| Benchmark | Sample size | Key metrics |
|---|---|---|
| claim_extraction_quality | 2 (worked example + negative case) | claims_extracted=2, relations_extracted=1, expected_subject_recall=1.0, no_entity_text_claim_count=0 |
| claim_verification_quality | 4 hand-labeled scenarios | accuracy=1.0 |
| nli_quality | 9 hand-labeled pairs (3/label) | accuracy=0.7778, entailment_accuracy=0.3333, neutral_accuracy=1.0, contradiction_accuracy=1.0 |
| recommendation_verification_quality | 5 hand-labeled scenarios | precision=1.0, recall=1.0, f1=1.0 |
| faithfulness_quality | 2 synthetic answers (faithful vs. hallucinated) | faithful_answer_score=1.0, hallucinated_answer_score=0.6, correctly_ranked=1.0, unsupported_claim_count=1, claim_coverage=0.5, calibration_error_brier=0.0671 |
| claim_verification_ablation | 2-claim synthetic scenario | disabled: 2/2 kept (0 checked); rule_based (no KG populated): 0/2 kept; rule_plus_graph (KG populated): 2/2 kept |
| nli_ablation | synthetic contradiction scenario | disabled: 0 contradictions found; rules (RuleBasedNLIDetector): 1 contradiction found |

**Honest reading of `nli_quality`**: overall accuracy (0.7778) hides a real
weak spot — `RuleBasedNLIDetector`'s entailment_accuracy is only **0.3333**
(1 of 3). Its entailment rule is a coarse lexical-overlap heuristic (near-
identical wording only); paraphrases with different wording but the same
meaning are correctly NOT flagged as contradictions (good) but also aren't
recognized as entailment (the honest cost of a conservative heuristic).
`neutral_accuracy`/`contradiction_accuracy` are both 1.0 on this hand-labeled
set — reported as-is, not tuned to hide the entailment gap. A real
transformer NLI model (`TransformerNLIDetector`, the default when a model
can load) would be expected to do meaningfully better on entailment; this
number specifically characterizes the always-available fallback.

**`claim_verification_ablation`'s `rule_based` (no Knowledge Graph
populated) configuration keeps 0 of 2 claims** — with an empty graph and no
other evidence corroborating each claim beyond its own origin chunk, both
claims land on `INSUFFICIENT_EVIDENCE` and get dropped. This is the real,
literal mechanism behind "unsupported claims never reach the narrator," not
a benchmark artifact — populating the graph (`rule_plus_graph`) is what
lets both claims reach `SUPPORTED`/`PARTIALLY_SUPPORTED` and survive.

**Reasoning Latency is not a separate benchmark** — every `BenchmarkReport`
above already carries a real measured `duration_seconds` (all sub-7ms on
this hardware for these small synthetic inputs, dominated by claim-graph
construction/traversal, not by any model inference — `nli_quality` and
`claim_verification_ablation` don't load a transformer model at all).

## Notes on methodology and limitations

- Documents are synthetically generated (seeded, deterministic) — see
  `app/research/datasets/generator.py`. Retrieval/entity ground truth is
  exact-string-match against generator-attached labels, so real-world
  paraphrased text would score lower than these numbers suggest.
- **Relation extraction scored 0 F1 in this synthetic run.** This is a real
  result worth stating plainly rather than hiding: it appears to be a gap
  between how `SyntheticDatasetGenerator` labels ground-truth relations and
  what the rule-based relation extractor's co-occurrence patterns actually
  match on a single chunk per document, not evidence that relation
  extraction is broken — the hand-written `demo_data/` scenario
  (see `demo_data/README.md`) does produce real, non-zero relations
  (1-2 per document) when ingested through the same production code path.
  Closing this gap in the synthetic benchmark itself is tracked as future work.
- **Prediction and recommendation benchmark numbers above are not meaningful
  signal in this run** — `actual_values` for the prediction benchmark is a
  placeholder constant (no real historical outcome data exists for freshly
  generated synthetic equipment tags), and the recommendation benchmark's
  feedback volume is 0 in a fresh, empty Learning Repository. Both numbers
  are included for completeness/transparency, not as a claim about
  prediction quality — see the dedicated Rule-based vs ML comparison below
  for a benchmark that *does* have real ground truth (real synthetic labels
  with a genuine held-out test split).
- The reasoning benchmark uses 8 deliberately-constructed conflicting
  evidence pairs (antonym state statements), not documents mined from
  the corpus above.
- Hybrid (no graph) already reaches recall@5 = 1.0 on this query set, so
  graph-aware retrieval's marginal contribution isn't isolated by this
  particular metric/query construction — it shows up in the *contents*
  of the evidence returned (synthesized graph-relation evidence, see
  `docs/architecture/retrieval.md#graph-expansion`), not in recall@5 here.
- Rule-based vs ML prediction compares on the *same* held-out rows from
  a single synthetic training run — see `docs/architecture/ml-lab.md`
  for why labels are synthetic-but-learnable rather than fabricated.
